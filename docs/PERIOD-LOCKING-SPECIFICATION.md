# Period Locking Specification

**Last verified:** 2026-09-14  
**Primary sources:** `src/period-locking.js`, `src/PeriodLockSettings.jsx`, `src/PeriodClosing.jsx`, `src/JournalEntriesPro.jsx`, `tests/period-scope-visibility.test.mjs`, `tests/period-lock-settings-ui.test.mjs`, `tests/period-unlock-scope.test.mjs`.

This document is the implementation specification for the Period Locking module: the data model, the settings and lock creation UI, the dynamic organisation and branch visibility rule, the enforcement layer, the API surface, the validation rules and the acceptance criteria for each scope configuration. Source and tests remain authoritative where this prose differs.

## 1. Data model

### 1.1 Storage

| Key | Owner | Content |
|---|---|---|
| `wayvida-period-control-v1` | `src/period-locking.js` | `periods[]`, `requests[]`, `audit[]`, `overrides[]` |
| `wayvida-period-settings-v1` | `src/period-locking.js` | The single locking policy record |

No new storage key was introduced. Both Period Closing and Settings read and write the policy through `readPeriodSettings` / `writePeriodSettings`, and `src/AccountingSettingsPanel.jsx` remains a second editor of the same record.

### 1.2 Policy record (`defaultPeriodSettings`)

- `lockingMode`: `Automatic` | `Manual` | `Off`.
- `schedule`: `frequency` (Day, Week, Month, Quarter, Year, Financial Year), `effectiveFrom`, `lockAfterDays`, `lockAtTime`, `notifyDaysBefore`, `timezone`, `weekStart`, `monthMode`, `monthStartDay`, `monthEndDay`, `quarterMode`, `yearMode`, `anniversaryDate`, `fyStartMonth`, `fyLabelFormat`.
- `approval`: require approval to unlock. `unlockPermission`, `defaultUnlockDuration`, `maximumUnlockDuration`, `unlockScope`, `approverRole`, `autoRelock`, `dailyAutoApproval`.
- `defaultScope`: `{companyIds[], branchIds[]}`.
- `exemptModules[]`: modules whose system-generated postings skip the lock check.
- Existing fields retained: `defaultType`, `defaultFrequency`, `reminderDays`, `autoLockAfterDays`, `closingDay`, `allowedRoles[]`, `automaticPeriodCreation`, `backdated`, `unlock`, `mandatoryChecks`, `warningChecks`.
- `autoLockPreviousMonth` is retained as a derived compatibility mirror of `lockingMode === 'Automatic'` so existing settings screens keep working. `normalisePeriodSettings` derives `Automatic` from a legacy record only when no explicit mode was stored.

### 1.3 Period record

`id`, `companyId`, `organisationName`, `scopeType` (`Organisation` | `Branches`), `branchIds[]`, `branchNames[]`, `modules[]`, `financialYearId`, `year`, `name`, `frequency`, `start`, `end`, `status`, `lockType`, `lockedBy`, `lockedAt`, `reason`, `approvalStatus`, `lastAction`, `transactionImpactCount`, `version`, plus temporary-unlock fields `lockTypeBeforeUnlock`, `unlockedBy`, `unlockedAt`, `unlockRequestId`, `unlockApprovalId`, `unlockExpiresAt`, `unlockManual`, `unlockScope`, `unlockStartDate`, `unlockEndDate`, `statusChangedBy` and `statusChangedAt`.

Engine statuses stay internal: `Open`, `Closing Review`, `Pending Approval`, `Soft Locked`, `Hard Locked`, `Pending Unlock Approval`, `Temporary Unlock`, `Reclosed`. `closingStatus()` maps them to the four display statuses `Open`, `Closing`, `Closed`, `Reopened`, which are the only statuses rendered.

### 1.4 Unlock request and override records

- Request: `id`, `periodId`, `period`, `companyId`, `organisationName`, `scopeType`, `branchIds[]`, `modules[]`, `requestedBy`, `reason`, `duration`, `requiredDuration`, `transactionType`, `amount`, `approver`, `affectedTransactionCount`, `status`, `date`, `approvedBy`, `approvedAt`, `approvalId`, `remarks`, `startAt`, `expiresAt`, `manual`, `autoReclose`, `unlockScope`, `unlockStartDate`, `unlockEndDate`, `cancelledBy`, `cancelledAt`, `decisionReason` and `expiredAt`.
- Override: `{id, periodId, period, user, date, operation, targetDate, reason}` appended to `overrides[]`, with a matching `Lock override` entry in `audit[]` carrying actor, timestamp, operation, target date, previous status, new status and reason.

## 2. Settings UI specification

Settings is a right-side popup drawer (`src/PeriodLockSettings.jsx`) that Period Closing opens into `pc-settings-drawer`. It renders `.pls.pls-popup`, so the surrounding drawer owns the geometry and the panel never takes over the page; it keeps a close button in its header, a sticky footer holding `Save changes` and `Cancel`, and a dirty-state guard that asks before discarding unsaved edits. The panel lead is a single sentence - `Locking applies to every module in Wayvida Books, and changes apply from the next unclosed period.` - replacing the earlier two-sentence scheduling paragraph. The panel now carries one settings card holding both switches and the closing schedule, and no other card. That card has no heading of its own, so the popup runs straight from its one-sentence lead into the switches. The popup itself is tuned for its 620px drawer: the card uses `padding:16px 18px` with a 12px internal gap, switch rows carry a hover state and a real toggle track, the schedule rows and the sticky footer were tightened, the sticky heading and footer carry a separation shadow, every surface shares one 22px gutter (16px below 760px), and `@media(max-width:760px)` reflows the grid, the warnings, the heading and the footer together. `.pls-popup .pls-close{display:inline-flex!important}` restores the close button, which the legacy global app-bar rule `@media(max-width:1050px){header>button:not(.primary):not(.hamb){display:none}}` was hiding below 1050px.

- The panel carries exactly one card, and it is headingless: the `Automatic locking` `<h2>`, its `Periods lock on this schedule, and a locked period refuses new or modified postings. Switch it off to create every lock by hand.` description and the read-only `policyChip()` label were all removed, so no text-only block sits above the controls. The former `Period locking` card and the `Unlock approval` card were folded into it, and the `More policy settings` disclosure was removed entirely.
- `Enable automatic locking` is the master switch of the card and only moves between `Automatic` and `Manual`: switched on it shows the schedule fields, switched off it makes locking manual. `lockingMode: 'Off'` is no longer reachable from this popup - Settings -> Accounting -> Period control maps `Off` <-> `Manual` on the same stored value - so while the stored mode is `Off` the switch is disabled (`label.pls-switch.pls-switch-off`, 55% opacity) and the card explains that period locking is switched off in Accounting settings. The engine keeps its three-state `lockingMode` and the popup only maps onto it, which is the brief's "manual is a disabled state" shape.
- Closing schedule fields: `Frequency`, `Effective from`, `Lock after period end`, `Lock at` and `Notify before locking`. While locking is manual or off these five fields are disabled (`pls-fields-off`), so manual mode has an explicitly inert schedule.
- Generated schedule: in Automatic mode the periods produced by the policy are listed read-only inside the same card with their date range, grace days and lock time; `No periods generated. Check the effective date and frequency.` is shown when the schedule is empty.
- Unlock approval is the second switch row of the same card, below a `pls-rule` divider: one `Require approval to unlock` toggle and nothing else. The `Unlock approval role` select and every other unlock control - default unlock duration (including `Until manually re-locked`), maximum unlock duration, unlock scope (whole period or a selected date range), automatic re-lock on expiry and daily auto-approval - left the popup; the engine keeps their normalised defaults and the unlock request flow still reads them. When approval is switched off the card states that no Request Unlock action is rendered anywhere and only an administrator written override remains, which is the only note the card carries in that state.
- `More policy settings` was removed. The frequency-boundary fine detail (week start, month mode with custom start/end day, quarter mode, year mode with anniversary date, FY start month and label format), organisation timezone, default scope, allowed roles, module exemptions and the read-only enforcement coverage list are no longer rendered anywhere: the popup is the schedule, the two switches and the warnings. Their values are untouched and stay engine defaults in `normalisePeriodSettings` (`defaultScope`, `allowedRoles`, `exemptModules`), so no stored policy and no lock behaviour changed.
- One `lockingMode` is the switch for the whole product, and Settings -> Accounting -> Period control reads and writes the same value instead of its own mirror: `Period locking` maps `Off` <-> `Manual` and `Automatic period closing` maps `Automatic` <-> `Manual`, both through `normalisePeriodSettings` and `writePeriodSettings`, with the automatic switch and the schedule fields disabled while locking is off. Its `Closing frequency` and `Close after days` fields edit `schedule.frequency` and `schedule.lockAfterDays`, the values the scheduler and the Period Closing popup actually use. The legacy `autoLockPreviousMonth` flag is a derived mirror of `lockingMode` and is never toggled directly - before this checkpoint the Settings toggle wrote that flag, which `normalisePeriodSettings` overwrote on save, so switching automatic locking on from Settings had no effect.
- Default scope: the shared organisation and branch selector described in section 4 left the popup, so `ScopeSelector` is now an exported-but-unrendered component kept for reuse; `PeriodLockSettings` no longer reads `defaultScope` or renders a scope card, and Period Closing still renders no scope selector of its own. `scopeVisibility` is consumed once, inside that exported component.
- Unsafe policies warn before saving: Automatic with approval off is a locked-forever configuration that requires explicit confirmation; a Daily schedule with approval on warns about unlock request volume and offers auto-approval.

### 2.1 Period Closing page layout

`src/PeriodClosing.jsx` is one lean single-purpose screen whose body is the locked-periods register. There is no tab row, no page subtitle and no status block above the card. Top to bottom:

- Heading row (`pc-heading`, the Journal Entries heading grid): the `Period Closing` title sits alone inside `pc-title-block` - the read-only policy chip and its single-child `pc-title-row` wrapper were removed from the heading - and a journal-style subheading (`pc-heading-note`, "Lock accounting periods and control when postings stop.") sits beneath them, so the heading reads like Journal Entries. The composite period/status/scope line, the locked-periods status line, the inline missing-periods row and the old page subtitle stay gone; the facts that remain in the product live on other surfaces (period name, status, dates, organisation and branch scope in the current-period popup; the failing-check and entries-affected counts in the heading's `Before you close` attention pill). The locked-period count, the last-locked period and the pending-request count left the page with the `Audit log / History` entry, and the locking policy is now read only inside Period Closing Settings.
- Page actions (`pc-heading-actions`, right-aligned): the read-only `Before you close` attention pill (`details.pc-attention-pop` > `summary.pc-attention-pill`, hidden while every check passes and given a slightly wider trailing gap so it reads as status rather than as a third action) first, then one `More actions` menu (`details.pc-more` > `summary.pc-more-btn` + `.pc-more-menu`) plus one separate `Create Lock / Close` button (`pc-create-lock`, rendered while locking is on and the role may lock). The menu holds two entries - `Current accounting period` (sub-labelled with the period name and its status) and `Period closing settings` (sub-labelled `Locking schedule and unlock approval`, opening the settings drawer). The `Audit log / History` entry and the wide lock-history drawer it opened were removed, so the filtered register is the only lock list. Each entry carries a one-line description and every entry closes the menu before it acts. Create Lock, the pre-close review, the unlock-requests view, the missing-periods action and the lock history surface do not live in this menu.
- Current period card (the default view): period name, dates, organisation and branch scope, a `Status` badge, and lock-aware inline actions - `Lock this period` while open, `Request Unlock` when closed with approval on, `Admin override` when closed with approval off, an `Unlocked until ...` note while reopened, and `View details`. The retired `Transactions`, `Audit log` and `Close with review` link row is removed.
- Locked periods register (`LockRegister`, `pc-locks-panel`): a `Locked Periods` / `Requests` toggle (`pc-view-toggle`, the leftmost element of the compact `div.pc-register-bar` toolbar, its requests half rendered only while unlock approval is on) switches the register body between the lock list and the unlock-request list, each half carrying its own count. The panel no longer renders the `Locked periods` / `Unlock requests` heading and the `Every lock for <organisation> ...` note beside the toggle; the toggle and its counts carry that meaning, and no caller passes `title` / `note` any more, so the bar is always the toggle plus its filters. The toolbar row is one compact `div.pc-register-bar`: the toggle on the left and, on the right, a search box and one `Filters` disclosure (`pc-filters-more` > `pc-filters-panel`, badged with the number of active filters). The `Period` select (every period name present in the current view) and the `Status` select (lock states in the locks view, request states in the requests view) now sit inside that panel ahead of Financial Year (defaulting to the current year through `CURRENT_FY`, with `All financial years` still offered), Organisation, Branch, Closed By and Closed Type (Manual / Automatic), plus `Clear filters`. Desktop renders `pc-history-table`; small screens render `pc-history-cards`.
- The `Requests` half of the register is one table - `div.pc-table-fit pc-request-table` in the register shell, the same fit geometry as the locked-periods table, so it never scrolls sideways - carrying seven columns: Period, one combined `Organisation & Branch` cell, Reason, Requested, Requested By, Status and Actions. The combined scope cell resolves through `requestScopeOf(request, periods)`: it finds the period the request belongs to (the request record itself carries only `scopeType` and `branchIds`, never branch names), prints that period's `organisationName` - falling back to the organisation's name in `demoOrganizations` so a stored code such as `ABC01` is never shown - and prints `periodBranchLabel()` of that period as the small line beneath it, so a whole-period lock reads `All branches` and a branch scope lists the real branch names (`Kochi Branch, Bengaluru Branch`). A request with no matching period in the current data still degrades cleanly to `All branches` rather than to raw ids. The Status cell holds the page's canonical `span.pc-badge` through `requestStatusLabel(request)`: a stored `Pending approval` reads `Requested`, and `Approved`, `Cancelled`, `Rejected` and any other stored status render unchanged (tone classes `.requested` amber, `.approved` green, `.cancelled` / `.rejected` red on the base grey). Unlock scope, duration, access-until and approver remarks are read from the row's `View Details` popup rather than from the table. Every row's Actions cell holds the same two controls: one read-only `View` button (`button.pc-request-view`) that opens `RequestDetailsDrawer`, and that row's 3-dot menu (`details.pc-kebab.pc-request-kebab` with `div.pc-kebab-menu.pc-request-kebab-menu`) holding `Approve`, `Cancel`, `View Details` and `Delete`. `View` and `View Details` open the same drawer - a right-side `pc-request-drawer` reading one request as a `dl.pc-request-facts` grid - so the cell never changes shape between rows. `Approve` renders only while the request is pending and the acting role may decide it, `Cancel` only while it is pending and the acting role raised it, and `Delete` for the requester or any approver, which removes the record through the engine's `deleteUnlockRequest` - a pending request is released first, exactly as `cancelUnlockRequest` does, and the removal writes its own `Unlock request deleted` audit entry. There is no reject option: an unlock request is approved or withdrawn. `decideUnlockRequest(state, {requestId, decision, user, reason})` still accepts `'Rejected'` so stored requests and the engine state machine stay valid, but no control produces it. The register renders every filtered request in one pass: the `Previous` / `Page <n> of <n>` / `Next` pager, the `REQUEST_PAGE_SIZE` constant and the list's `page` state were all removed, so no row is ever held back, and the Branch filter now applies to the requests half (`branchMatch`) exactly as it already did to the lock list. The acting role is the first role the policy allows (`allowedRoles[0]`, `Admin` by default) and it is also the role that raises requests, so a self-raised request is decided as the next authorised approver instead of dead-ending: the page resolves `unlockApproverFor(requestedBy, settings)` from the engine (the same `['Business Owner','Admin']` order the daily auto-approval uses, skipping the requester, any role the policy excludes and any role without `approve-unlock`), threads it into `RequestList` as `approver`, and records the decision under that name. The row never restates the approver: the cell is the read-only `View` button beside the row menu, so a pending decision offers `Approve` in that menu and nothing else. When the policy leaves no other approver the row keeps `Another approver must review your own request.` with no decision buttons, and a role without `approve-unlock` still reads `Approval requires an approver role.`
- Register columns: Period, Organisation, Branch, Status, Closed Date, Closed By and Actions. The kebab menu (`pc-kebab-menu`) holds `View Requests` (only while approval is on), `View Audit Log` and `View Details`, plus `Request Unlock` on a closed period or `Close Period` on an open one.
- Row visibility follows the locking mode through the engine helper `lockRegisterRows(periods, {mode, today, createdIds})`: `Automatic` keeps only locks whose period has already ended (`period.end < today` and a `Closed` display status), so future locks never appear; `Manual` keeps only periods whose lock was created in this app, identified by an audit entry with the action `Lock period created` or `Period closed` (`createdLockIds`), so the seeded demonstration locks stay out of the manual list and a lock appears the moment the user creates it; `Off` hides nothing. When the list is empty in manual mode the register explains itself with `No locks created yet. Use Create Lock / Close to lock a period for every module.` instead of the generic no-match text.
- Missing periods are out of scope for the page: the inline row, the `Create missing periods` action and the `findMissingPeriods` / `generateFinancialYearPeriods` wiring left `src/PeriodClosing.jsx`, and `missing` / `createMissing` / `attentionTotal` were deleted with them. The engine still exports both helpers (covered by `tests/period-locking.test.mjs`) but no page surface offers them.
- `Before you close` is a compact, never-dismissible attention pill in the heading action group (`details.pc-attention-pop` > `summary.pc-attention-pill`) instead of the full-width strip that used to sit under the heading. The pill carries an amber warning icon plus the count as text (`3 checks`, never a bare number) and the accessible label `Review <n> checks that need attention`; it has no trailing chevron because it opens a popover rather than navigating. One computed tone drives fill, border and ink - `.neutral` grey (`#f4f6f9` / `#e2e6ed` / `#4a5468`) for one or two soft checks, `.warn` for three or more (`rgba(234,88,12,.07)` / `#f0d3b8` / `#9a3412`) and `.danger` red (`rgba(220,38,38,.06)` / `#f3c9cd` / `#b42318`) when a check actually blocks the close - and the primary blue is never used, because that belongs to `Create Lock / Close`. Clicking it opens `div.pc-attention-pop-menu` (width `min(400px,92vw)`, anchored `top:calc(100% + 8px);right:0`), the one place the review is *looked* at: its head states `Before you close` with `<n> checks need attention · <m> entries affected`, then `Checklist` (rendered with the `only` prop, so passed checks are filtered out) lists each failing check with its count and its filtered-entries link, and a `Review all` action opens the `panel==='before'` pre-close review drawer (`pc-before-drawer`). The drawer keeps the entries-affected count, the wrapped category chips (Sales, Purchases, Expenses, Banking, Journal Entries) and the per-check review links; its duplicated body heading, the sentence `The system verifies the following before <period> can be closed.` and the readiness pill (`pc-ready-pill` with its `ready` / `warn` / `blocked` states) were removed, so the body runs from the chips straight into the checklist. `attention` is one memo (`readiness.checks.filter(check=>check.state!=='Passed')` plus the entries-affected count and the tone), so the pill, its tone, the popover summary and `aria-live="polite"` count can never disagree; a count of zero hides the whole `details`, and `All checks passed` is printed inside the popover only. The popover carries no close action, because `Create Lock / Close` remains the page's only close entry point.
- The register toolbar is one compact row inside `<div className="pc-register-bar">`: the `Locked Periods` / `Requests` toggle sits on the left, while the right side holds the reused `.pc-filters` row containing the search box and the `Filters` disclosure. `Period` and `Status` live inside the `.pc-filters-panel`, ahead of `Financial Year`, `Organisation`, `Branch`, `Closed By` and `Closed Type`, so the visible row never grows past the toggle, the search box and `Filters`; the `advanced` badge counts the two moved filters as well. The bar is a `<div>` rather than a `<header>` on purpose, because the legacy global app-bar element rules in `src/styles.css` (`header label{height:38px;background:#f6f8fb;padding:0 12px}`, `header input{...}`, `header>button{...}`) restyle any label, input or button inside any header in the application.
- The `Activity History` block (`Closing, reopen and approval events for this period.`) is removed from `CurrentPeriodPanel` together with the `currentTimeline` memo, so a period's activity is read in the `View details` drawer and in the per-row `View Audit Log` drawer, which keep their own `Timeline`. The acting role belongs to the global `VIEW AS` control, and the `Create Lock / Close` button beside `More actions` is the page's only close entry point, so two competing close buttons can never render.
- The current accounting period is no longer a card on the page. It opens from the first `More actions` entry (`Current accounting period`, sub-labelled with `currentMeta` - the period name and its status) as the `panel==='current'` right-side drawer (`pc-current-drawer`, 520px). The drawer body renders the real `CurrentPeriodPanel` (now a named export, so the render harnesses exercise the shipped component): the status eyebrow, the period name, the `01 Sept 2026 – 30 Sept 2026 · ABC Technologies Pvt Ltd · All branches` line, the status badge and the one action the status allows - `Lock this period` while open, `Request Unlock` while closed with approval on, `Admin override` while closed with approval off, the unlocked-until note while reopened - plus `View details`. In the drawer the card is flattened: the icon is dropped, the copy takes the full width, `display:flex!important` beats the 900px grid reflow, the duplicate eyebrow is hidden under the drawer title and the period line wraps instead of truncating. When no period is configured the popup renders the `No current period` empty state instead of crashing.

### 2.2 Drawer shell and page chrome

Every Period Closing drawer is portalled into `document.body` and wrapped in `<div className="pc pc-portal-scope">`; `.pc.pc-portal-scope{display:contents}` supplies the `.pc` reset hooks without adding a layout box.
The Period Locking Settings drawer is the deliberate exception to the wrapper rule: it keeps the canonical `.pc-history-drawer` shell class but not the `.pc` scope wrapper, so the page base-control rules (`.pc button`, `.pc input`, `.pc select`) cannot reach the panel. `src/period-lock-settings.css` therefore neutralises the legacy global top-bar `header` rule for its own headings with `.pls header{position:static;inset:auto;width:auto;height:auto;min-height:0;max-width:none;z-index:auto;margin:0}`. Without that reset the panel heading inherited `position:fixed;height:58px`, and while the card still carried a title every `.pls-card>header` stacked on top of the others at the top of the viewport. Because `.pls-popup` is portalled inside the host `.pc-history-drawer`, the reset also matches that drawer's own `<header>`, which is harmless: `src/period-closing.css` already declares the same static geometry with `!important` on `.pc-history-drawer>header` because the drawer header is intentionally a static flex row and `pc-drawer-body` is its only scroll container. That wrapper is what isolates the drawer from the legacy shell rule `aside{position:fixed;inset:0 auto 0 0;width:206px}`, which otherwise pins a portalled drawer to the 206px navigation rail. Each drawer then declares its own geometry - `position:fixed`, `right:0`, `z-index:1400`, a block scrim at `z-index:1390`, `width:min(<n>px,96vw)`, and a flex column whose `pc-drawer-body` is the only scroll container - with widths of 1080px for the wide lock history register (`min(820px,94vw)` between 760px and 1100px), 620px for settings, 560px for lock, override, audit, details and the pre-close review, 520px for unlock requests and the current accounting period popup, all full width on small screens. Every drawer and modal close button is a direct child of a `header`, which the legacy global rule `@media(max-width:1050px){header>button:not(.primary):not(.hamb){display:none}}` hid below 1050px; `src/period-closing.css` restores them with `.pc-history-drawer>header>button,.pc-modal>section>header>button{display:inline-flex!important}`. A drawer header is fixed at `padding:18px 22px` with a bottom hairline and drawer actions sit in `pc-drawer-footer`, so scrolling the body never moves them. The settings panel scrolls inside that host as `.pls.pls-popup` with a sticky heading and a sticky footer.

Page chrome follows the Journal Entries heading grid and one gutter per level: the panel shell owns the border and radius while its header, toolbar row and register are borderless children, the `Before you close` and settings card headers reset the legacy top-bar `header` styling, and the current-period card switches to explicit grid placement below 900px rather than a hard-coded left offset.

None of this changes storage, the close/lock/audit flow or any enforcement rule; it is styling plus the portal wrapper and one labelled filter wrapper in the page markup.

## 3. Lock creation UI specification

- Manual mode: the `Create Lock / Close` button beside `More actions` opens a right-side drawer with `Select period` (Month, Quarter, Year, Financial Year), a `Date` field whose helper line previews the resolved range through `resolveLockRange`, and an optional `Reason (optional)`. Creating it locks that organisation for every module - no scope selector, no lock name and no lock strength are shown - and a blank reason falls back to the system note `Manual lock created for all modules` so the lock stays auditable. One lock is created per organisation in scope.
- Automatic mode: the same `Create Lock / Close` button opens the drawer in schedule mode. It renders the five policy inputs that drive the schedule - `Frequency`, `Effective from`, `Lock after period end`, `Lock at` and `Notify before locking` - seeded from the saved policy and editable for this run only (`pc-lock-fields`). The drawer resolves the target through `autoTarget()`, which walks `generatedSchedule()` from the effective date and skips every range that is already locked or conflicted, then prints it as `Next lock: <period> · <start> to <end> · locks <n> day(s) after the period ends at <time>` (`pc-lock-preview`). When no slot is free the preview turns amber with `Every period on this schedule is already locked for <organisation>.` and `Create Lock` is disabled. The automatic run still creates the lock through `createLockWindow` + `lockPeriod` and records the cadence in the audit reason (`Automatic schedule: locks <n> day(s) after the period ends at <time>, notifying <n> day(s) before postings stop`), so close, lock and audit logic is unchanged.
- Locking off: no lock action is rendered.

## 4. Dynamic organisation and branch visibility

```
orgCount = number of organisations in the selected scope
anySelectedOrgHasMultipleBranches = any selected organisation owns two or more branches
showOrgColumn = orgCount > 1
showBranchColumn = orgCount > 1 or anySelectedOrgHasMultipleBranches
```

| Organisation configuration | Branch configuration | Journal line columns |
|---|---|---|
| 1 organisation | 1 branch | Hide Organisation and Branch |
| 1 organisation | Multiple branches | Show Branch only, filtered to that organisation |
| Multiple organisations | Branches | Show Organisation and Branch |

Behaviour:

- The read-only context strip (`Locking for: Organisation . Branch|All branches`) is always rendered. The context is never hidden together with the field.
- An organisation that owns exactly one branch auto-fills it and renders it as read-only text, never as a one-option dropdown.
- Branch options always come from the organisation in the same row; branches of another organisation never appear.
- Changing the organisation re-resolves the branch to that organisation's only branch, or clears it when there are several.
- Branch is required only when the organisation owns more than one branch.
- An organisation with zero branches is treated as the lock unit and shows a dash in the branch cell.
- Visibility is re-evaluated on every scope or configuration change through the shared scope module, not only on page load.

Implementation (single source of truth): `src/organisation-scope.js` owns this rule for the whole accounting module. `getScopeVisibility({organisations,organisationIds|companyIds,branchIds,label})` (alias `scopeVisibility`) returns the resolved rows, the read-only `strip` context line and the flags `showOrganisation` / `showBranch` (aliases `showOrgColumn` / `showBranchColumn`), and `getBranchesForOrganisation(reference,organisations)` is the only branch lookup. `organisationBranches()` annotates each branch with its owning organisation, `selectedOrganisations()` resolves the scope list, `normaliseScope()` auto-fills a one-option branch and clears a foreign selection, `validateScope()` returns `OK` / `NO_SCOPE` / `UNKNOWN_ORGANISATION` / `BRANCH_NOT_IN_ORGANISATION` / `BRANCH_REQUIRED` and `scopeLabel(row)` composes the `Organisation · Branch` text. `NO_BRANCH` is the em dash shown for a branchless organisation and `ALL_BRANCHES` is `All branches`. `src/period-locking.js` re-exports these helpers rather than keeping its own copy, and the same module is consumed by Period Locking settings, Create Lock, Create Journal Entry -> Journal Lines and Chart of Accounts (create, edit, listing and details).

- Period Locking consumers: `ScopeSelector` in `src/PeriodLockSettings.jsx` renders the strip and both columns from `getScopeVisibility` and resolves a branch with `getBranchesForOrganisation`; creating a lock validates its scope with `validateScope`, so an unknown organisation code or a branch belonging to another organisation is rejected instead of silently dropped.
- The Create Lock / Close drawer renders the shared `OrganisationBranchScope` picker over the available working context (`getAccessibleOrganizations()`), so the selector only appears when the context justifies it: one organisation with one branch states `Locking for: ABC Technologies Pvt Ltd · Kochi Branch` and shows nothing selectable, one organisation with several branches offers the Branch list alone (defaulting to `All branches`, so a whole-organisation lock is never silently narrowed), and several organisations offer Organisation and Branch with the branch list filtered to the owner. The popup prints no scope chip and no schedule paragraph - on the user instruction of 2026-09-14 its header is only the mode label (`Manual locking` / `Automatic locking`) and the `Create Lock / Close` title - so the scope shown is the selectors themselves, and the picker's `onChange` writes `companyIds` / `branchIds` straight into `createLockWindow`.
- The request unlock drawer renders the same control with `showFields={false}`, stating `Unlocking for: <organisation> · <branch scope>` from the locked period. The scope of an unlock request is derived by `requestPeriodUnlock` from the locked period, so it is presented, not chosen - a branch-narrowed unlock request would need a new enforcement rule for temporary unlocks and is deliberately not faked in the UI.

## 5. Enforcement layer

`assertOperationAllowed()` is the single enforcement entry point. Enforced operations are create, edit, delete, post, post-draft, backdate, allocation, inventory, depreciation, accrual, revaluation and import or bank feed writes. System-generated postings follow the same rule unless their module is listed in `exemptModules`.

- A locked date is blocked by any active lock covering it; unlocking one lock does not unlock an overlapping one.
- `blockingLocksFor()` sorts overlapping locks by start and end date so the reported lock is deterministic.
- Rejections return the blocking lock and a remedy that names the lock and explains how to request an unlock, or states that only an administrator can apply a written override when approval is off.
- `applyAdminOverride()` requires an administrator or configure role and a written reason, and appends both an override record and an audit entry.
- `lockingMode === 'Off'` short-circuits enforcement and reports `lockingDisabled`.
- `assertOperationAllowed()` fails closed when the resolved lock state cannot be read (no `periods` array). It returns `allowed:false` with code `PERIOD_NOT_CONFIGURED` and a remedy explaining that the lock state could not be read, instead of throwing inside a posting path. A configured store with no matching period returns the same code with a different message.
- The Create Journal Entry page resolves its date through `assertOperationAllowed({operation:'post',...})`, so a rejected posting names the blocking lock and the inline date hint shows that lock name next to the existing Request unlock action.

## 7. Validation rules

1. Policy changes apply from the next unclosed period and never reopen, rewrite or remove an existing lock.
2. A date is locked when any active lock covers it.
3. Financial-year locks are evaluated per organisation because FY start months can differ.
4. No user may approve their own unlock request.
5. Automatic mode with approval disabled requires explicit confirmation before saving.
6. Daily frequency with approval enabled warns about request volume and offers auto-approval for daily locks.
7. Every lock, unlock, approval, expiry, rejection and policy change writes to the audit trail with actor, timestamp, before value, after value and reason.
8. Manual lock creation requires a reason and a scope that passes `validateScope`: at least one organisation, an organisation that still exists, and every named branch inside a selected organisation. A one-option branch and a branchless organisation resolve themselves rather than failing.
9. An approved unlock expires after its configured duration, re-locks automatically and records both events; `Until manually re-locked` never expires automatically.
10. An unlock request must sit completely inside the locked period, and an approved date-range window releases only the dates it names.
11. A pending unlock request can be cancelled by its requester or an approver; a decided or expired request cannot.
12. When the lock state cannot be resolved, enforcement fails closed rather than allowing the write.
13. Organisation and branch visibility is derived from the shared scope module, never from a per-screen copy of the rule.

## 8. Acceptance criteria

- A date-range unlock releases only dates inside its approved window; other dates in the same period stay blocked.
- A pending unlock request can be cancelled by its requester or an approver, and the previous lock returns.
- An unlock that expires writes both the `Unlock expired` and `Period reclosed` audit events and preserves the request history.
- Every locking audit entry carries actor, timestamp, action, organisation, branch, before value, after value, reason and the related request id.

- One organisation with one branch hides both columns and shows the read-only context strip.
- One organisation with multiple branches hides Organisation and shows Branch, filtered to that organisation.
- Multiple organisations show both columns, with Branch always filtered to the selected Organisation.
- A branch from another organisation is never accepted: it is cleared by `normaliseScope` on selection and rejected by `validateScope` on submission, and `getBranchesForOrganisation` never returns it.
- Changing frequency from Monthly to Quarterly leaves every existing lock untouched.
- Turning approval off removes every Request Unlock action, the register's `View Requests` entry and the status-line `Open unlock requests` action without leaving empty states.
- An entry dated inside a locked period is rejected, and the rejection explains which lock blocked it and how to request an unlock.
- An approved unlock expires after its configured duration, re-locks automatically, and records both events in the audit log.

## 9. Assumptions where the brief was silent

- The settings page keeps the existing `wayvida-period-settings-v1` record and the legacy `autoLockPreviousMonth` mirror instead of adding a second policy store, so the existing Accounting Settings editor keeps working.
- The engine still validates a lock type (`lockPeriod` accepts `['Soft Lock','Hard Lock']`) and the UI still sends one, but it is never chosen or displayed: `newForm` / `newLockForm` hold a fixed `lockType:'Hard Lock'`, no form field, column or filter exposes it, and the `Lock type` row was removed from `DetailsDrawer`'s summary, so the only Auto/Manual vocabulary on the page is the `Closed Type` filter. The brief asks for a basic manual lock that applies to every module, so the `Create Lock / Close` drawer exposes only the period, the date and an optional reason; a blank reason becomes the system note `Manual lock created for all modules` so every lock stays auditable.
- Setting a lock name edits the created period record and its audit entries rather than storing a display alias.
- The automatic generated schedule is listed read-only on the settings page, where the scope is still editable, rather than in Period Closing, because automatic mode has no manual create action.
- The organisation timezone is shown read-only; the prototype stores the configured label and does not perform timezone maths.
- The brief describes automatic locking as one enable switch plus a disabled manual state, so the settings UI exposes `Lock periods` and `Enable automatic locking`. The engine keeps its three-state `lockingMode` (`Automatic`, `Manual`, `Off`) and the two switches only map onto it, so no engine contract changed.
- Where an edge case is not covered by the brief, the safest option chosen is to fail closed: unknown or blocked dates are rejected, off-locking is the only configuration that allows posting, and overrides always require an administrator and a written reason.

## 10. Unlock lifecycle: scope, cancellation and expiry

An unlock request carries the lock, the requested unlock scope, the start and end date, the requested duration and the reason. `unlockWindowFor(period, {unlockScope, startDate, endDate})` resolves that request against the lock itself:

- `Whole period` records the entire lock range (`period.start` to `period.end`).
- `Selected date range` requires both dates, requires the start to be on or before the end, and rejects any range that is not completely inside the locked period with a message naming the period and its range. No request can escape the original locked period.
- `requestPeriodUnlock()` stores `unlockScope`, `unlockStartDate` and `unlockEndDate` on the request and on its `Unlock requested` audit entry.

Approval copies the window onto the period, and `validatePeriodAction()` then allows only dates inside that window: a date in the same period but outside the window stays blocked with code `PERIOD_HARD_LOCKED` and a message that names the window. `blockingLocksFor()` applies the same window, so overlapping locks stay independently enforceable and one approved window never releases a date that another lock owns.

Deletion: `deleteUnlockRequest(state, {requestId, user, now})` is available to the requester or an approver on any request and removes the record from `state.requests`, writing an `Unlock request deleted` audit entry. A `Pending approval` request is released through `cancelUnlockRequest` first, so the period leaves the pending-approval state before its row disappears; deleting a decided request never rewrites its outcome.

Cancellation: `cancelUnlockRequest(state, {requestId, user, reason, now})` is available to the requester or an approver while the request is `Pending approval`. It restores the previous lock status (Hard Locked or Soft Locked), marks the request `Cancelled` with `cancelledBy`, `cancelledAt` and `decisionReason`, and writes an `Unlock cancelled` audit entry. A decided or expired request cannot be cancelled.

Expiry: `relockExpiredPeriods()` flips the matching request to `Expired` with `expiredAt` while preserving its reason and history, clears the unlock window fields, sets the period to `Reclosed`, and writes two audit entries - `Unlock expired` then `Period reclosed` - both attributed to the explicit `System` actor and both carrying the related request id. `Until manually re-locked` never expires automatically.

Policy changes: `recordPolicyChange(state, {previous, next, user, now})` writes nothing when the policy is unchanged, and otherwise writes a `Policy changed` audit entry with `beforeValue`, `afterValue`, the `policyChangeGuard()` message and `entityType: 'PeriodLockPolicy'`, then stores the new policy. Existing locks keep their scope, reason and history.

Period Closing exposes the scope: the unlock drawer collects the requested scope and, for a selected range, bounded start and end dates, the requests panel shows each request's scope, and a pending request raised by the current simulated role can be cancelled.

## 11. Audit record

Every locking event - lock created, unlock requested, approved, rejected, cancelled, expired, period automatically re-locked, policy changed and admin override - is written through one shared record builder, so each entry carries the fields the brief requires: `user` (the actor, or `System` for automatic actions), `date` (timestamp), `action` (the event), `organisation`, `branch`, `beforeValue`, `afterValue`, `reason` and the related lock or request id (`periodId`, `requestId`).

`organisation` resolves from the period, the unlock request, or the shared `ABC01` / `NSR02` / `MTC03` / `BWS04` name map; a global policy change is attributed to `All organisations` rather than to one company. `branch` names the branches in scope and falls back to `All branches` for organisation-scope locks. `beforeValue` and `afterValue` default to the previous and new status and are overridden where a richer snapshot exists, as in a policy change. `reason` falls back to the recorded remarks.
