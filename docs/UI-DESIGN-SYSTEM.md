# UI Design System

**Last verified:** 2026-09-21

## Conditional create form and the searchable picker

- Group a long record form into `section.itemSection` blocks that follow the operator's mental order, and put the rare fields behind the existing `details.itemAdvanced` disclosure instead of rendering everything at once. The Create / Edit Customer form reads Customer details, GST & Tax Details, Billing address, Payment & accounting, then More details.
- Prefer progressive disclosure to disabling. Hide a field entirely until its trigger is chosen - GSTIN / UIN only for treatments that carry one, the exemption reason only when Tax Exempt, the shipping block only when it differs from billing - and mark the trigger's options so the choice is obvious.
- Reach for the shared `SearchSelect` (`src/SearchSelect.jsx` over `src/search-select.css`) whenever a list is long enough to scroll - a place of supply, a customer, an account. Prefer it to a native `select` for anything an operator will search by name. It follows `src/AccountGroupPicker.jsx`: a `role="combobox"` trigger over a `role="listbox"` popover with a search input and its own search icon, ArrowUp / ArrowDown, Enter, Escape and an outside `pointerdown` that closes it, on the create-page field tokens (a 40px control on `#d7e0eb` with a 7px radius, a 9px-radius popover, 34px option rows, `#f4f7ff` / `#245fd9` for the active row). `options` takes plain strings or `{value,label,hint}` records and `onChange` always hands back the `value`, so a list of names and a list of records share one control; an empty trigger shows the search icon beside its placeholder so the control reads as searchable before it is opened. Mount it in a `div`, never inside a `label`, so label activation cannot re-fire the trigger when an option row is clicked, and keep its sheet scoped to its own root so it still outranks a host page that styles bare `button` / `input` elements.
- Keep every new control on the existing create-page tokens; do not introduce a second input, button or upload style. The GSTIN lookup reuses the shared `itemInputAction` row, the documents upload reuses `itemImageUpload`, and the repeaters put `itemFormGrid` rows inside `li` cards.
- Keep a row menu predictable: list the same actions on every row and disable the ones the engine refuses with the reason stated, instead of hiding them and leaving the operator guessing. Destructive entries carry the danger treatment, and a delete of anything that has posted is refused in the engine as well as in the menu.
- Open a document preview only on request, from an explicit Preview action, and render it in place of the detail screen the way Journal Entries does. Reuse the shell that already matches the document: the internal voucher preview for internal documents, the customer-facing document preview for sales and purchase documents.
- Condense a register by merging paired facts into one cell rather than by hiding them: an identity cell (Reference over Date), a classification cell (Type over Entry mode), a scope cell (Organisation over Branch) and a quantity cell (count over amount), each primary line full-strength and the second line through the shared `td small`. When a fact leaves the register because of a merge, it must already be on the detail screen - the reason, the adjustment account and the creator left the Inventory Adjustments register only because Adjustment information carries them, and the entry mode was added to that panel when the register started showing it.
- Render a status with the shared pill (`src/StatusPill.jsx` over `src/status-pill.css`), never a page-local badge. A detail screen is not exempt: the invoice detail carried its own `ivStatus` badge in the header and coloured `ivStatusText` inside its figures, which is the same status drawn three ways on one page. Render the pill in the header, in the figures row and in any section that states a status, and keep one `TONES` map per document type beside the component so the vocabulary stays in one place. It is the Chart of Accounts shape - `padding:4px 9px`, `border-radius:14px`, a 7px dot and a 12px/550 label - exposed as one component so every register reads the same. Pass `<StatusPill status="..." tone="ok|neutral|warn|info|violet|danger"/>`; callers keep their own status vocabulary and only choose the tone. Do not add a second badge style; if a page needs a new colour, add a tone to the shared sheet so all pages agree.
- Mark an exclusive choice in a repeater with a toggle button, not a checkbox. A bare checkbox reads as an unlabelled form field inside a card; a `button` with `aria-pressed`, a resting label that states the action (`Set as Primary Contact`), a check icon and a filled tint when active states both the action and the current state. Keep it on the same height and hairline as the row's other actions, and let `space-between` hold it opposite the destructive action.
- Wrap a wide field with `itemFieldWide` (`grid-column:1/-1`) inside the create grid, and fold repeaters from three columns to two below 900px and to one below 600px.
- Density on a record create page: three fields per row on a wide screen (two below 1100px, one below 700px) on a `14px 16px` gap keeps a long form short without hiding anything. Reach that with a three-class rule such as `.customersPage .itemCreatePage .itemFormGrid` so it outranks the shared two-class `.itemCreatePage .itemFormGrid` in `src/items.css` instead of editing that shared rule.
- Separate a full-width control that introduces a group - a radio or segmented choice - from the field grid below it with a small bottom margin (`.itemTypeField{margin:0 0 16px}`), because a `fieldset` followed directly by a grid reads as one overlapping block.
- When a validated field lives inside a collapsed disclosure, make the disclosure controlled and open it from the failed save, so a required-but-hidden error can never block the form invisibly.
- State a control's real behaviour in the interface. Get Taxpayer Details reports "GST details fetched successfully" beside the GSTIN when the backend answers, and the standard failure sentence through the same notice pattern when it does not - never a silent no-op.
- Three traps inside a page that already has component rules, all found by rendering the Sales Orders page in headless Chrome rather than by reading the CSS. The third has the same shape as the second but for bare elements: src/invoice-workspace.css is imported after the page stylesheet and styles h2, h3, small and textarea inside .invoiceWorkspace, so a single-class component rule loses and the create head title silently rendered at 23px instead of 16px. Prefix every component rule on such a page with the page's own class - .soCreatePage h2 - rather than relying on a component class alone. First, a shared toolbar rule reaches everything nested inside it: `src/items.css` styles `.itemsTools label` as the bordered search pill, so a filter panel placed in that toolbar had every field boxed and its caption centred until the panel explicitly reset the rule at equal-or-higher specificity. Second, a page-level element rule outranks a single-class component rule - `.invoiceWorkspace button` beat `.soAddressBackdrop` and painted a modal backdrop solid white - so a component mounted inside such a page must either raise its selector or pin the property. Check specificity against the host page before assuming a one-class rule wins, and prefer rendering the page to confirm.
- Never use a bare `<header>` (or `<footer>`) as a component's own heading: `src/styles.css` styles `header` as the fixed 58px application bar, which is what painted two address-card headings as strips across the top of the viewport. Use a `div` with a class, the way the create pages already do.
- Keep an external-data lookup behind an application route. The browser module posts to a relative path (`/api/gst/lookup`) and nothing else; the provider URL and the API key live in the hosting worker environment. When the lookup cannot run, fill the values the identifier itself carries and leave every field editable, so a failed lookup degrades into manual entry instead of blocking the form.
- Print a value the record inherits instead of offering a second place to edit it. The Sales Order line shows the item's unit as read-only text (`span.soUnitValue`) because the Item master already owns it; keep that on the order branch only - a screen whose engine still requires a unit per line, and which allows a free-typed line with no item to copy one from, has to keep the input; keep the cell at the row's 40px line so the numeric cells beside it stay aligned, and print an em dash until the parent record is chosen. The same rule applies to any field a picker copies in.
- When two controls share one cell, pin both sides of the pair. A number and its unit selector (the discount `%` / `₹`) only fit if the number yields (`flex:1 1 0`, `width:auto`) and the selector keeps a fixed basis with a floor, inside an `overflow:hidden` row - laying them both out at the shared `width:100%` pushes the selector out of the cell where nothing can see it.
- Never advertise a limit the storage cannot honour. The sales-order attachments tile promised ten files of 5 MB each against a browser store of roughly 5 MB; it now declares 10 files / 1 MB each / 2 MB in total, builds its helper text from the same constant the reader enforces, and turns a full store into `Browser storage is full. Remove an attachment or clear some saved data, then save again.` rather than the raw quota error. Check what the persistence layer can actually hold before writing the copy.
- State a fact once and say when it is the same. A read-only address block shows the billing address only; a shipping address that matches is one sentence (`Shipping address is the same.`) with the action that splits it, and its own row appears only when the two really differ. Showing two identical blocks, or a combined `Billing & shipping address` label, makes the reader check whether they differ at all.
- Anchor a summary's heading to the figures it names, not to the card. A totals block on the right of a wide card must carry its own width and right alignment (`width:min(420px,100%);margin-left:auto`) so the heading sits directly above the panel; left at the card's edge it reads as a heading for the whole band and the figures look orphaned.
- Read an overview as the document itself, in the order a reader checks it: who it is for, what it costs, what it contains, what has been paid, then everything else. The invoice overview is Customer, Invoice summary (Subtotal / Discount / GST / Round off, a rule, then Total / Paid / Balance), Items (Item / Qty / Rate / **Tax rate** / Amount), Payments (a count badge and one row per payment: date, method, amount) and one collapsed **More details** disclosure holding the reference facts - order number and status, dates, place of supply, salesperson, organisation, branch, notes. Do not give reference data its own panel beside the money it does not affect: it lengthens the page and buries the document. Watch the units when formatting a stored line - `money()` takes paise while a stored rate is the entered rupee string, which printed a ₹1,000 rate as ₹10.00.
- When a page must match another page's control, share the class AND restate its values under the page class. The invoice tab row carries `itemDetailTabs` so the two screens share one control, but that alone was not enough: `src/invoice-workspace.css` styles every bare `button` at class-plus-element specificity, which ties with `.itemDetailTabs button` and leaves the look to whichever sheet loads last - the invoice tabs were picking up a 6px radius and losing the Item Details hover tint. The page-scoped restatement is the fix, and a test that parses both rule sets and compares them property by property is what stops the copy drifting. Allow only differences you can name and justify.
- Standardise a tab row on ONE shape per module. The invoice detail first used three equal columns across a full-width card; measured side by side with the Item Details row it read as three separate controls, because the labels ended up ~90px apart with a wide dead gap between them. It now uses the module's own underline row - `display:flex;gap:0` with `flex:0 0 auto` buttons on a 12px gutter and a 2px underline on the active tab - which is the same control Credit Notes, Receipts, Item Details and Budgets already use. Prefer the shape the rest of the module already renders over a fresh arrangement that only looks tidy in isolation.
- Reuse the record-detail vocabulary of a neighbouring screen instead of restyling the same facts. The invoice detail's Overview now renders with the Item Details classes - `itemDetailCard`, `itemDetailSectionTitle` (the `#f9fbfd` tinted strip with an icon and an h2), `itemDetailFacts` (the dt/dd grid) and the `itemDetailTabs` row - so the two screens share one border, one radius, one title strip and one fact treatment by construction rather than by copying values. When a page asks to look like another, borrow its classes; only add a rule where the new context genuinely differs (here: two fact columns and a two-column section grid, because the cards are half width, and `.ivFactWide` for the addresses that wrap).
- Open a record detail screen the way the create pages open: one arrow-led full-bleed head (`Back` + the screen name + a hint naming the record) sitting directly under the working-context strip, then the content on the standard gutter. A breadcrumb strip above the same title, plus a coloured eyebrow repeating the record type, is two rows of chrome saying one thing - both were removed from the invoice detail screen. Gather everything that identifies the record - number, lifecycle pill, party, actions, the headline figures and the tab row - into ONE card with the tab body inside it, so the screen reads as a document rather than as four stacked bands; keep that card `overflow:visible`, because an actions menu opens inside it. Fold a tab whose content is simply a section of the record (its line items, its payments) into the overview rather than giving it a tab of its own.
- Render a value that the record inherits as a read-only definition list, never as a bordered box. The Sales Order customer panel is `dl.soFactList` with a 12px muted `dt` over a 13px strong `dd` - the same shape the Item Details page uses for its read-only facts - so it cannot be mistaken for a row of empty inputs; put one `p.soFactCaption` above it naming where the values came from, because a read-only value with no cue reads as an unfilled field. Keep the row on `align-items:start` so one short value does not leave a tall empty box beside it, and keep every label on one line height (`dt{display:flex;align-items:center;min-height:30px}`) so a label whose row also carries a button does not drop below the plain labels next to it - a single stray button made the whole row look broken until the labels shared one baseline. Keep an editable field out of such a row entirely: the Sales Order's Place of supply first sat inside the read-only facts and had to move out to the order-fields section, because one select among six values reads as a mistake however it is styled. Never convert such a value into an input to make it look consistent.
- Do not repeat a status in the same viewport. The invoice detail stated the lifecycle status in the header pill and then again as the first figure; that tile now states the linked order's number and status instead, and the fact was removed from the folded detail below. Before adding a figure, check whether the header already says it. And when a pill sits in a column flex container, give the container `align-items:flex-start` - the default stretch made a 104px pill fill its 276px tile.
- Put the two things an operator alternates between side by side rather than in stacked full-width bands. The Create / Edit Sales Order page opens on a 60/40 row - the customer on the left, the order fields on the right - because the customer's summary is then read where the customer is chosen, and the page loses a full-width band. Use `align-items:stretch` so the pair is one height, and stack to one column below the width where the narrower column would start crushing fields. Remember a grid item stretches its margin box: any `margin-top` on the second card (the usual stacked-card separator) is subtracted from its border box and the two cards end up a few pixels apart - drop that margin inside the row with a selector one class heavier than the rule that set it. Let the shorter card's extra room sit under its last row as card padding; distributing the rows with `align-content:space-between` fills the box but loosens the field rhythm away from the neighbouring card and reads as stretched. A fact list must change shape with its column, not just shrink: five facts across 1065px become one fact per line (label left, value right, a hairline between rows) inside a 420px column, with the long-value rows that also carry an action kept stacked. When a row spans two tracks in the wide variant, release it to `grid-column:auto` in the narrow one - a `span 2` inside a single-column grid creates an implicit second column and silently re-flow the list. Likewise, pair a grid down (four columns to two) when it moves into a 60% column, and restore the wider count when the cards stack.
- Keep a form's action bar inside the scrolling flow and sticky to the bottom, and check the ancestor chain before believing it: an action bar that scrolled off the screen was not a sticky bug but an `overflow-y:auto` on `#root` in the page's own scroll rule, because any overflow other than `visible` makes that element the nearest scrollport and the bar then pins to the bottom of a box exactly as tall as its own content. Release `height` and set `overflow:visible` on every ancestor between the bar and the element that really scrolls; paint the bar edge to edge, with the negative gutter and the page background, so content cannot show through behind it.
- Give file upload a drop zone, not a bare `input type=file`. Reuse the tile the Create Item page already uses for its image - a 36px tinted icon, one hairline, the shared focus ring - and make `onDragOver` / `onDragLeave` / `onDrop` feed the same reader the file input uses, so a dropped file and a chosen file cannot diverge. Print the real limit next to the action, and list each stored file as a row with its name, a human-readable size and its own remove button.
- Treat a line-level remove as a destructive action, not a bare icon: a 32px square on the shared 7px radius, the 16px `IconTrash` centred, `#b42318` on `#fff5f4` with a `#f0c8c4` hairline, darkening on hover. Reset the row's `padding:0` squeeze so the icon has room.
- Compare class-level specificity **and import order** before overriding a shared width or floor. A one-class page rule and a two-class host rule can tie on specificity, and then the sheet imported later wins outright: `.soCreatePage .ivLineTable{min-width:0}` never applied because `.invoiceWorkspace .ivLineTable{min-width:980px}` ties it and `src/invoice-workspace.css` loads after `src/sales-orders.css`, which left a 980px table floor that scrolled below 1440px. Add the element (`table.ivLineTable`) or an extra class to break the tie, and re-measure at 1280 / 1100 / 980 rather than only at the development width - a shared `!important` width (`.ivSearchInput input{width:230px!important}`) needs its own `!important` override at higher specificity.

## Item Details document page

- Place the full-width `itemDetailHead` directly beneath Working Context. It contains only the 40px back button and the `Item Details` title; restore the standard responsive gutter through `itemDetailBody` below it.
- Keep item identity and actions in one responsive card: image/icon, name and `Goods/Service · unit · HSN/SAC` on the left; lifecycle status, Edit Item and the canonical More actions menu on the right. Stack the actions below identity at narrow widths without hiding them.
- Use one tab row for Basic Data, Transactions and History. Show transaction/history counts as a pill inside their labels, identify the selected tab with `aria-current="page"`, and render only the active information card to reduce page length and scanning effort. The row is full width and every tab is an equal cell, so all three labels and their count pills stay visible without a horizontal scrollbar.
- Keep one 14px vertical rhythm between the identity card, the tab strip and the section cards, and 16px of padding inside every card. `itemDetailBody` is `display:flex;flex-direction:column;gap:14px;margin:16px clamp(16px,2.2vw,28px) 0`, `itemDetailFacts` is `padding:16px` over a `16px 22px` grid gap, table cells are `10px/11px 16px`, and the page ends with the existing 32px `.itemDetailPage` bottom padding. Never re-add a second body bottom margin: it doubled the space under the last card and left the dead band that used to sit between the identity card and the first section card.
- Keep the Item Details header one card: the identity row and the tab bar share a single panel. `div.itemDetailPanel` wraps `div.itemDetailIdentity` and `nav.itemDetailTabs`, and the panel is `background:#fff;border:1px solid #e6ebf2;border-radius:10px` with **no** `overflow:hidden` - that would clip the More actions menu opening from the identity row. The identity row keeps its own grid and `padding:14px 16px` but contributes no border, radius or background of its own. `.itemDetailTabs` is the panel footer, not a pill: `display:flex;align-items:center;flex:0 0 auto;gap:0;height:46px;padding:0 4px;border-top:1px solid #e6ebf2;background:transparent;overflow:hidden`, with every tab a content-sized `flex:0 0 auto;width:auto;min-width:0;height:100%` cell at `0 12px` padding, no vertical separators, a transparent 2px bottom border that turns `#3478f6` on `.active`, and `white-space:nowrap`; the 4px bar padding plus the tab's 12px padding lines the first label up with the 16px card gutter, and below 700px the bar padding drops to `0` to follow the 12px gutter. Below 520px the tabs go back to `flex:1 1 0` equal cells with `0 8px` padding and a 12px label. `gap:0` and `overflow:hidden` are what remove the space between the tabs and stop the row ever scrolling sideways. This bullet previously required equal `flex:1 1 0` tabs across the full content width; a 2026-09-17 user request to reduce the gaps between Basic Data, Transactions and History superseded that, because equal thirds on a wide screen pushed the three labels hundreds of pixels apart - the tabs now size to their own labels. `width:auto` is required on those tabs, not decorative: `src/styles.css` declares a bare `nav button{width:100%}`, and with `flex:0 0 auto` the flex base size comes from `width`, so omitting `width:auto` makes every tab as wide as the whole bar and `overflow:hidden` then clips Transactions and History off the right edge - the exact regression a user reported on 2026-09-17; the old `flex:1 1 0` masked it behind flex-basis:0. The 520px fallback is not optional and must be declared after the base rules: it previously sat inside the shared `@media(max-width:520px)` block above them, where the base rule overrode it at equal specificity, so the small-screen layout never applied. The explicit height plus `flex:0 0 auto` is still the guard that stops an ancestor from stretching the bar into a tall empty box; never fall back to a `min-height`-only shape, never restore the old `padding:4px;gap:4px;overflow-x:auto` pill strip, and never split the identity row and the tab bar back into two separate cards. The Customers detail page (`src/customers.css`) reuses this exact geometry with its own `.customerDetailPanel` / `.customerDetailIdentity` / `.customerDetailTabs` classes - one panel card owning the identity row and the tab footer, content-sized `width:auto` tabs, the same 520px equal-cell fallback declared after the base rules, and the same deliberate absence of `overflow:hidden` so the identity-row More actions menu (`z-index:90`) is not clipped - and its tab labels are `Basic Data`, `Transactions` and `History`. Create and Edit Customer is a full-bleed page on the same shell as Create Item (`form.itemCreatePage`), not a modal popup: one `div.itemDialogHead` with a square `button.itemBack` beside `div.itemHeadText`, one `div.itemDialogBody` card of three `section.itemSection` blocks labelled by plain `div.itemSectionTitle` elements, and the shared fixed `footer.itemDialogFooter` action bar. The create page body must keep `overscroll-behavior:auto` on `.itemCreatePage .itemDialogBody`: `src/ui-system.css` gives `.itemDialogBody` `overscroll-behavior:contain`, and with the card's own `overflow:hidden` that trapped the wheel over every field, so only the head bar, the footer and the page gutter scrolled the page.
- Keep the identity card a 48px icon or image tile beside the name, print the saved SKU in the meta line (`No SKU · Goods/Service · unit · HSN/SAC code`), and keep the Edit Item button and the More-actions trigger both 36px tall.
- Do not repeat `Item Details` as another body heading. Working Context, the document header, item identity and task content are separate visual levels.

### Customer receipt detail
- A detail page joins the document-detail family by carrying the shell marker class, not by copying markup: `ivDetailOpen` on the workspace section releases the shell padding (`body:has(.ivDetailOpen) .app>main{max-width:none;padding:0}`), and the order inside the card is always the arrow head, then `ivDetailBody > ivDetailSheet`, then identity row, figures row, tab row and one padded body.
- Reuse the tab row rather than restyling a local one: `nav.itemDetailTabs.ivDetailTabs` is the one underline row for every detail page and for nested view switchers inside a tab body.
- When a detail page needs a control that belongs with the tabs, put it inside a wrapper row (`div.receiptTabsRow`) and give the wrapper the divider, then force the nav's own `border-top:0`. A rule painted on the nav alone stops under the last tab and leaves the trailing control outside the line.
- Bundle order decides which rule wins at equal specificity: `src/receipts.css` loads before `src/invoice-detail.css`, so a receipt rule that must beat `.ivDetailSheet .itemDetailTabs` has to add a class (`.receiptWorkspace .ivDetailSheet>.receiptTabsRow>.itemDetailTabs`) rather than rely on order.
- The receipt detail's figures row is `Receipt date / Payment mode / Received into / Received / Available to allocate / Allocation`, and the lifecycle is the shared `StatusPill` on `RECEIPT_TONES`. Keep the legacy `.receiptContext`, `.receiptWorkspace .ivSummary`, `receiptLedgerTabs{flex-wrap:wrap}` and `receiptWorkspace .ivTabs` rules deleted.

### Purchases: the module joins the shells
- A page inside `.app>main` gets the whole design system for free; a page mounted through `createPortal` gets none of it. Purchases was portalled, so it had to be moved first: the module now routes through `App.jsx` beside the sales pages and carries `invoiceWorkspace purchaseWorkspace`, with `soCreatePage ivCreatePage` on its document create pages (Create/Edit Vendor is the one exception, on the shared `itemCreatePage` create page) and `ivDetailOpen` on its detail pages. Never reintroduce `.purchasePortal` or `.vendorPortal`.
- One class pairing, not one stylesheet per screen: `invoiceWorkspace purchaseWorkspace` brings the shared type, buttons, labels, inputs, tables and `ivHeading` / `ivCard` / `ivTools` / `ivActions` geometry, and `.welcome:has(+.invoiceWorkspace)` suppresses the welcome block. Add a `.purchaseWorkspace` rule only when the shared layer genuinely has no equivalent - today that is the workspace width, the register foot, the detail-sheet gutter, `purchaseTabBody` and the wrapping `.purchaseDetailLines` table.
- A percentage width cannot hold free text. `.receiptTable th,.receiptTable td{overflow:hidden;text-overflow:ellipsis}` over a table-level `white-space:nowrap` quietly cuts a mode line, a hand-typed reference or a list of invoice numbers, and no column width will hold all of them. Widen what can be widened and let the free-text columns wrap with `white-space:normal;overflow-wrap:anywhere`: `overflow-wrap` breaks an unbreakable token rather than letting it spill over the neighbouring cell, and leaving `text-overflow:ellipsis` in place keeps a truncation signal as the last resort. Measure `scrollWidth` against `clientWidth` per cell rather than trusting the declared percentages, and give the Actions column the pixel slack it needs for `button + gap + trigger + cell padding` - on the receipts register 14% fitted by 0px and the `.ivScroll` wrapper grew a horizontal scrollbar.
- Give a row action a matching trigger, and check how its menu opens before you move it. A visible row button beside a differently-styled kebab reads as two unrelated controls, so restate the trigger to the row-button geometry - the invoices, sales orders and payment receipts registers all run a 36px square with the same border and radius. Then check whether that page portals its menu or opens it in normal table flow: a page that keeps the panel in flow must leave the `details` `display:inline-block`, because as a flex item the open panel is shrunk to the column width.
- `table.ivInvoiceTable` is `table-layout:fixed`, and `src/invoice-workspace.css` gives its first seven columns percentage widths that total 100% from `.invoiceWorkspace .ivInvoiceTable th:nth-child(n)`. A column added with no declared width collapses to zero and its header and controls disappear; a column added *with* one takes its share and the browser scales every other column down to fit, which reads as a proportions bug rather than a missing rule. Any table that wears `ivInvoiceTable` beside its own class must therefore declare its widths from a selector that outranks that one - repeat the section class and the element, as `.receiptWorkspace table.receiptTable th:nth-child(n)` does - and make the whole set total exactly 100% in one block. When a register of eight or ten columns is needed, that is supported: the Payment Receipts register carries eight and the credit note register ten, each declaring its own set. Fold a fact under a neighbouring cell as a `small` when it is a detail of that cell, not as a way to avoid the width rules. The detail line tables override `table-layout` instead, under `.purchaseDetailLines`.
- Registers: `ivHeading` → `ivCard.ivRegisterCard` → `ivTools` with `ivToolSearch` and one `soFiltersMore` disclosure → `ivScroll > ivInvoiceTable` → `ivRowActions` with one View button and one portalled 3-dot menu → `ivActions.purchaseRegisterFoot` count. Status uses the shared `StatusPill` with a page-local tone mapper; do not restore `.purchaseStatus` or `.vendorStatus`. The magnifier `IconSearch` belongs to the `ivToolSearch` pill alone: the `soFiltersMore` summary carries the 17px `IconFilter` on every register (`src/CreditNotes.jsx`, `src/InvoiceWorkspace.jsx`, `src/Purchases.jsx`, `src/PurchaseReports.jsx`, `src/SalesOrders.jsx`, `src/Vendors.jsx`, `src/DebitNotes.jsx`, `src/GoodsReceipts.jsx`, `src/VendorPayments.jsx`), so a filter control never advertises itself with the search icon.
- Create pages: purchase documents use `soCreatePage ivCreatePage` + `div.soCreateHead` (40px `soBack`, `h2`, `small.soHeadHint`) + `form.ivCreateForm` of `ivCard`/`ivFields` sections + `ivLineTable` + `soBillingSummary` + `details.ivCard.soMoreCard` + pinned `div.ivFooter.soActionBar`. ### Organisation and branch scope

One rule decides whether an Organisation selector and a Branch selector are rendered anywhere in the accounting module, and it lives in one place: `src/organisation-scope.js`. - Card headers inside the `.pc` scope explicitly reset `padding`, `background` and `border`, because the legacy global `header` rule otherwise applies the fixed application top bar white background, hairline border and `8px 16px` padding to every nested card header.
- The current accounting period popup (`panel==='current'`, `pc-current-drawer`, 520px) reuses the period card as its body and flattens it for the drawer: the icon is dropped, the copy takes the full width, the card's own eyebrow is hidden under the drawer title, the period line wraps instead of truncating, and `display:flex!important` overrides the card's 900px grid reflow. It renders the status badge and exactly the one action the status allows - `Lock this period`, `Request Unlock`, `Admin override` or the unlocked-until note - plus `View details`, and falls back to the `No current period` empty state when no period is configured.
- Never put page controls inside a `<header>` unless you neutralise the legacy global app-bar element rules in `src/styles.css`: `header{position:fixed;height:58px;padding:8px 16px}`, `header label{width:min(320px,27vw);height:38px;background:#f6f8fb;padding:0 12px}`, `header input{border:0;background:none;width:100%}`, `header>button{height:38px;border:1px solid #e5eaf1;border-radius:6px}` and, below 1050px, `header>button:not(.primary):not(.hamb){display:none}`. That is why the Period Lock register toolbar is a `div.pc-register-bar` and why every drawer and modal close button needs an explicit `display:inline-flex!important` (`.pc-history-drawer>header>button,.pc-modal>section>header>button` and `.pls-popup .pls-close`); without it the close buttons vanish on any viewport narrower than 1050px.
### Empty states

Every table or list that can render no records uses the shared `src/EmptyState.jsx` component instead of a bare sentence: `EmptyState({variant,title,description,action,actionLabel,onAction,className})` renders `div.emptyState` (a centred flex column, `min-height:250px`, `32px 20px` padding, no forced scroll) holding `svg.emptyArt` (`viewBox="0 0 96 96"`, `aria-hidden="true"`, one plate at `fill:#f4f7fb` and one `#94a3b8` stroke glyph), `h3.emptyTitle` (15px/650), `p.emptyText` (13px, `max-width:430px`) and an optional `div.emptyAction > button.emptyCta` that reuses the primary button. The variants `budget`, `lock`, `request`, `journal`, `adjustment`, `customer` and `default` share that plate, stroke weight and grey - never a second illustration style, an emoji or a large colourful graphic.

The component is not only a table fallback: a form slot that would otherwise print placeholder values uses it too. The customer card on both sales create pages renders EmptyState variant customer until a customer is chosen, so eight Not recorded / Not registered / Not provided facts never stand in for a customer who has not been selected. Bound it to the space the filled content occupies - .soCreatePage .soCustomerEmpty{min-height:284px;padding:20px;gap:8px} with a 78px illustration - because an unbounded empty state is what stops a two-card row staying level. An empty slot also drops the controls that act on the missing record: the customer card's edit pencil appears only once a customer is chosen. Those two cards also carry no caption under their headings: a heading names the card, and the control under it already says what to do, so a sentence repeating it is deleted rather than reworded.

Render it as a row inside the table body so it sits in the table's own content area: `tr.emptyStateRow > td.emptyStateCell` with the column count as `colSpan` (the card-list form uses `div.emptyStateHost` instead). The triple-class `td.emptyStateCell.emptyStateCell.emptyStateCell` rule clears the cell padding, `.emptyStateRow,.emptyStateRow:hover` clears the row hover fill, and no table header, filter or pagination changes. Offer the primary action only when the user can create the missing record - Budgets, Period Locks, Journals and Inventory Adjustments do; Unlock Requests, which appear when someone else submits them, do not.

The artwork animates itself in from the same stylesheet - a staggered entrance of about a second, then a slow rest: `emptyArtIn` fades and lifts the `svg` 5px, `emptyPlateIn` scales the plate from 0.9 to 1, the three `.emptyBar` budget bars grow in from `transform-origin:50% 100%` at 0.15 / 0.27 / 0.39s, the `.emptyDraw` and `.emptyDrawLate` strokes draw themselves with `stroke-dashoffset` (0.75s, with `:nth-of-type` delays so a shackle or a page flap follows the shape it belongs to), and an `.emptyDot` keyhole pulses; once the entrance is over the glyph rests on a very slow 7s `emptyBreathe`. The base state of every shape is its finished drawing, so a browser that runs no animation shows the complete illustration, and `@media (prefers-reduced-motion:reduce){.emptyState .emptyArt,.emptyState .emptyArt *{animation:none!important}}` removes all of it. Never animate anything outside the illustration, never let the motion shift the table or take focus, and never make the component's meaning depend on it.

## Responsive behavior

- Sidebar becomes a controlled drawer on narrow screens.
- Header actions may simplify but core navigation and creation remain available.
- Cards reflow without clipped values or text overlap.
- Wide tables retain accessible horizontal scrolling and may hide secondary columns whose values remain available in details.
- Interactive targets should be approximately 40–44px where practical.
- Period History collapses from a full desktop table to compact scrolling and then to a card list, with each card carrying period, organisation, branch, status, closing metadata, and its row actions.

## Accessibility

- Provide semantic headings, table headers, labels, button names, status text, and visible focus states.
- Icon-only controls require accessible names and tooltips where meaning is not obvious.
- Maintain adequate foreground/background contrast.
- Drawers and modals require close controls, Escape/focus management in production, and focus restoration.
- Side drawers open from the right throughout the application. They use a dimmed backdrop, a left border and negative-x shadow, isolate nested `header`/`aside` elements from shell positioning, remain viewport-bound, and become full width on small screens. Centered confirmation/action dialogs remain modals and are not converted into drawers.
- `ui-quality-polish.css`, loaded after module styles, is the authoritative placement layer for side drawers. New modules should reuse the existing drawer families instead of adding a left-edge override.
- Announce validation and asynchronous state changes to assistive technology.

## Customer documents

Preview opens only after explicit Preview action. Keep preview embedded in the app shell. The toolbar contains Print, Share, Customize, and Close. Customize opens a right drawer and stays closed initially. The preview stylesheet isolates nested header, navigation, main, and aside elements from legacy global shell positioning so the toolbar and document canvas never overlap. Print hides app chrome and prints only the document. Templates preserve document type/status, company logo, statutory identity, customer details, item table, taxes, totals, amount in words, notes, and signature. Template changes never recalculate or repost accounting.

Document detail pages use a separate arrow-led breadcrumb above the document identity. The identity row includes document type, number, party, and a semantic lifecycle badge. Actions are ordered by task importance: one primary next action, neutral secondary actions, and a restrained destructive action. Four compact summary metrics precede a tab strip. The Overview tab places document information and amount summary side by side on wide screens and stacks them on small screens without removing data. Items, Payments, Accounting, and Audit content remain accessible from their existing tabs.
Period Lock is a focused register rather than a dashboard of summary cards. Its feature stylesheet must explicitly reset nested `header` and `aside` positioning because legacy global selectors otherwise make those elements fixed. The Period Locking Settings panel renders inside the same drawer host as `.pls.pls-popup`, which resets its legacy full-page positioning so the drawer and not the panel owns the geometry. At desktop widths it begins after the 270px navigation rail and below the 59px application header; on narrow screens it uses the full content width and preserves horizontal access to the accounting table.
## Application-wide UI quality layer

`src/ui-quality-polish.css` is the final, UI-only compatibility layer loaded by `src/main.jsx`. It normalizes focus, hover, active and disabled states; 40px form controls; readable table density; status semantics; viewport-safe overlays; toolbar wrapping; deliberate empty states; reduced-motion behavior; and the shared 270px navigation/58px header portal geometry. It must not contain persistence, accounting, calculation, route, permission, or workflow logic.

Responsive safeguards target 1440px desktop through 1280px and 1024px laptop/tablet layouts, then collapse dashboard portals and form grids below the existing mobile navigation breakpoint. Tables retain local overflow only when their columns cannot reflow safely; the page body remains protected from horizontal overflow.

- A table that must never scroll sideways needs `table-layout:fixed` with percentage columns, not a smaller `min-width`. A content-driven table is sized by its widest cell, so shaving padding only moves the problem; a fixed layout cannot exceed its wrapper whatever the content. Size any inner widget that carries a fixed width in a shared sheet - an item search, a tax selector - to its own column here, and then check every cell for clipping, because a cell can fit its column while its contents are cut off.
