# UI Design System

**Last verified:** 2026-09-17

## Item Details document page

- Place the full-width `itemDetailHead` directly beneath Working Context. It contains only the 40px back button and the `Item Details` title; restore the standard responsive gutter through `itemDetailBody` below it.
- Keep item identity and actions in one responsive card: image/icon, name and `Goods/Service · unit · HSN/SAC` on the left; lifecycle status, Edit Item and the canonical More actions menu on the right. Stack the actions below identity at narrow widths without hiding them.
- Use one tab row for Basic Data, Transactions and History. Show transaction/history counts as a pill inside their labels, identify the selected tab with `aria-current="page"`, and render only the active information card to reduce page length and scanning effort. The row is full width and every tab is an equal cell, so all three labels and their count pills stay visible without a horizontal scrollbar.
- Keep one 14px vertical rhythm between the identity card, the tab strip and the section cards, and 16px of padding inside every card. `itemDetailBody` is `display:flex;flex-direction:column;gap:14px;margin:16px clamp(16px,2.2vw,28px) 0`, `itemDetailFacts` is `padding:16px` over a `16px 22px` grid gap, table cells are `10px/11px 16px`, and the page ends with the existing 32px `.itemDetailPage` bottom padding. Never re-add a second body bottom margin: it doubled the space under the last card and left the dead band that used to sit between the identity card and the first section card.
- Keep the Item Details header one card: the identity row and the tab bar share a single panel. `div.itemDetailPanel` wraps `div.itemDetailIdentity` and `nav.itemDetailTabs`, and the panel is `background:#fff;border:1px solid #e6ebf2;border-radius:10px` with **no** `overflow:hidden` - that would clip the More actions menu opening from the identity row. The identity row keeps its own grid and `padding:14px 16px` but contributes no border, radius or background of its own. `.itemDetailTabs` is the panel footer, not a pill: `display:flex;align-items:center;flex:0 0 auto;gap:0;height:46px;padding:0 4px;border-top:1px solid #e6ebf2;background:transparent;overflow:hidden`, with every tab a content-sized `flex:0 0 auto;width:auto;min-width:0;height:100%` cell at `0 12px` padding, no vertical separators, a transparent 2px bottom border that turns `#3478f6` on `.active`, and `white-space:nowrap`; the 4px bar padding plus the tab's 12px padding lines the first label up with the 16px card gutter, and below 700px the bar padding drops to `0` to follow the 12px gutter. Below 520px the tabs go back to `flex:1 1 0` equal cells with `0 8px` padding and a 12px label. `gap:0` and `overflow:hidden` are what remove the space between the tabs and stop the row ever scrolling sideways. This bullet previously required equal `flex:1 1 0` tabs across the full content width; a 2026-09-17 user request to reduce the gaps between Basic Data, Transactions and History superseded that, because equal thirds on a wide screen pushed the three labels hundreds of pixels apart - the tabs now size to their own labels. `width:auto` is required on those tabs, not decorative: `src/styles.css` declares a bare `nav button{width:100%}`, and with `flex:0 0 auto` the flex base size comes from `width`, so omitting `width:auto` makes every tab as wide as the whole bar and `overflow:hidden` then clips Transactions and History off the right edge - the exact regression a user reported on 2026-09-17; the old `flex:1 1 0` masked it behind flex-basis:0. The 520px fallback is not optional and must be declared after the base rules: it previously sat inside the shared `@media(max-width:520px)` block above them, where the base rule overrode it at equal specificity, so the small-screen layout never applied. The explicit height plus `flex:0 0 auto` is still the guard that stops an ancestor from stretching the bar into a tall empty box; never fall back to a `min-height`-only shape, never restore the old `padding:4px;gap:4px;overflow-x:auto` pill strip, and never split the identity row and the tab bar back into two separate cards. The Customers detail page (`src/customers.css`) reuses this exact geometry with its own `.customerDetailPanel` / `.customerDetailIdentity` / `.customerDetailTabs` classes - one panel card owning the identity row and the tab footer, content-sized `width:auto` tabs, the same 520px equal-cell fallback declared after the base rules, and the same deliberate absence of `overflow:hidden` so the identity-row More actions menu (`z-index:90`) is not clipped - and its tab labels are `Basic Data`, `Transactions` and `History`. Create and Edit Customer is a full-bleed page on the same shell as Create Item (`form.itemCreatePage`), not a modal popup: one `div.itemDialogHead` with a square `button.itemBack` beside `div.itemHeadText`, one `div.itemDialogBody` card of three `section.itemSection` blocks labelled by plain `div.itemSectionTitle` elements, and the shared fixed `footer.itemDialogFooter` action bar. The create page body must keep `overscroll-behavior:auto` on `.itemCreatePage .itemDialogBody`: `src/ui-system.css` gives `.itemDialogBody` `overscroll-behavior:contain`, and with the card's own `overflow:hidden` that trapped the wheel over every field, so only the head bar, the footer and the page gutter scrolled the page.
- Keep the identity card a 48px icon or image tile beside the name, print the saved SKU in the meta line (`No SKU · Goods/Service · unit · HSN/SAC code`), and keep the Edit Item button and the More-actions trigger both 36px tall.
- Do not repeat `Item Details` as another body heading. Working Context, the document header, item identity and task content are separate visual levels.

## Inventory Adjustment create header

- Place `div.iaCreateHead` directly beneath the Working Context bar; remove the shell main padding only while `section.iaPage` has `iaCreatePage`.
- Keep the back button in the first title row, 40px on desktop and 36px below 700px, followed directly by the New/Edit Inventory Adjustment title. Do not restore the redundant Inventory eyebrow or descriptive subtitle.
- Keep lifecycle status visible without competing with the title: right-aligned on desktop and beneath the title gutter on narrow screens.
- Restore the standard responsive gutter on every create-screen block after the header and reset the main scroll port to the top when changing Inventory Adjustment screens.
- Keep the create page field-first: do not render Step labels, the Adjustment details or Items headings, or the removed explanatory section copy. `iaItemsControlBar` contains only Entry mode and Add Item.
- Label the compact type selector `Mode of adjustment`, show Reference Number before Date, use Account and Description, and label the quantity grid Item Details, Quantity Available, New Quantity on hand and Quantity Adjusted. Keep Location because posting is branch/location keyed.
- A missing stock-item dependency is an actionable amber `iaItemsEmptyAlert`, not repeated helper copy inside every row. Its Create Item button navigates to Items; Add Item and the final posting/submission action remain disabled until the dependency exists. Keep Save as Draft available.
- Keep the create footer sticky inside the main scroll port and let the inventory-impact definition list form separated responsive value cells rather than one compressed run of labels.

## Chart of Accounts header

- Show the selected-context account total once, in the page title: `Chart of Accounts (N)`.
- Place the plain-language description directly below the title.
- Use the shared compact Working Context bar below the application header; do not repeat context inside the page.
- Open context customization in a right-side drawer with organization/branch search and multi-selection enabled by default; do not present a separate selection-mode chooser.
- Use modern square checkboxes with clear selected, hover, and focus states. Hovering the context summaries reveals the complete selected organization or branch list.
- Keep the drawer compact: no eyebrow label or explanatory multi-selection banner; prioritize visible organization and branch rows to minimize scrolling.
- Follow the page header with a compact Assets, Liabilities, Equity, Income, and Expenses summary strip, then the grouped account grid.
- The account grid uses Checkbox, Account Name, Account Code, Account Type, Opening Balance, Current Balance, Status, and Actions columns.
- Accounting actions and behavior remain unchanged.

Semantic page headers rendered inside portals must reset legacy shell header geometry (`position`, `inset`, fixed height, padding, border, and background). Page titles and actions remain in normal document flow beneath the application toolbar.

Company, branch, and financial-year selectors live in a dedicated global context bar immediately below the primary application header. The primary header is reserved for search, quick create, notifications, help, settings, and the user profile. Portal workspaces begin below both header rows.

## Foundations

- Product name: **Wayvida Books**.
- Use the supplied transparent Wayvida logo from `public/`.
- Primary font: Instrument Sans with a readable system fallback.
- Minimum visible font size: 12px, including tables, helper text, chart labels, and mobile controls.
- Core palette: white surfaces, cool gray page background/borders, dark navy text, blue primary/action color, restrained semantic green/amber/red.
- Prefer subtle borders and low-elevation shadows; avoid dense stacks of nested cards.

## Shell and navigation

- Keep the persistent dashboard sidebar and header for normal app pages.
- Dashboard is a standalone top-level destination.
- Use expandable navigation groups with a clear active child. `Budgets` is one flat destination inside the Accounting section (`leaf('Budgets')` in the sidebar, declared between the Journal Entries and Period Closing leaves), not a group of its own: the Budget sub-group and the separate Budget Reports and Budget Settings pages are deleted, so keep them gone. The sidebar leaf is the only budget navigation: no budget screen renders a section tab row of its own, so keep `budgetWorkspaceTabs` deleted and never thread a navigation callback into the budget screen.
- Back navigation uses a left arrow and explicit destination label within the page header.
- Company, branch, and financial-year selectors live in the global header.

## Forms and workflows

- Use progressive disclosure: essential fields first, accounting/advanced options collapsed or separated.
- Full-page creation forms remain inside the dashboard shell.
- Group related fields into clearly titled sections with stable footer actions.
- Preserve user input after validation failure.
- Show loading, empty, error, success, and disabled states.

### Create Journal Entry

The manual journal page is a compact accountant workflow, not an ERP admin form. Reach for this pattern when a form has a small mandatory header and a repeating line grid.

- Keep a single mandatory metadata row holding date, journal type, optional reference and the reason for entry. The reason is a plain single-line input, not a description box, and it is never duplicated inside the disclosure.
- Do not put a posting-context card on that page. The organisation and branch are chosen per line, so the page must not render a Posting To summary box, a Change popover or any second context store, and it must not write the working-context storage keys.
- Report a locked accounting period inline with the date input - a compact lock hint plus a small inline unlock action inside the date field - and only while the selected period is genuinely locked. Never show a period error while the chosen date sits in an open period, and never use a separate warning banner.
- Keep organisation and branch directly editable per line, placed between the account and the debit column, but only while the working context makes that choice ambiguous: one accessible organisation hides the Organisation column, and a single branch under it hides Branch as well. The line grid therefore renders seven columns (several organisations), six (one organisation with several branches, or one organisation and one branch only when a stale line still needs it) or five, and the visibility decision comes from the shared scope module below rather than a page-local copy, and the variants keep the Debit, Credit, Description and row-action columns sized like the full grid; the columns are addressed by the `je-head-amount` and `je-cell-amount` classes rather than by position so a hidden column cannot shift their alignment. When a column is hidden, say so once in the Journal lines subtitle (for example `Posting to <organisation> · <branch>`) instead of adding a second selector, and never render a duplicate organisation or branch control. Filter the Branch dropdown to the selected organisation only, reset a line's branch as soon as its organisation changes, and keep every line on an organisation and branch that still exist in the working context. The selects store the organisation and branch names already used by `emptyLine()` and `postToLedger()`, so the posting contract does not change.
- Hide system-generated identifiers until the record exists, then show them as read-only context.
- Make mutually exclusive monetary fields visibly exclusive: entering a debit disables that row's credit input and the reverse.
- Move optional work behind a collapsed disclosure while keeping the primary action visible in a sticky footer.
- Place row-adding controls below the grid so the action follows the last row.
- Close the Journal lines grid with one footer row whose right end carries Total Debit and Total Credit together with the balance status, so the posting condition reads as part of the amounts it describes and the row costs no extra height. Stack the status on its own line directly beneath those amounts inside the same right-aligned block rather than setting it beside them, so `Debit equals credit` or `Difference: <amount>` reads as the caption to the figures above it. Show the balance status as the only posting indicator on the page.
- Keep the Additional details disclosure for the read-only approval comments only, summarised by their count, and render it only when the journal actually carries approval comments so an empty disclosure never appears.
- Put the single Attach files button at the left of that same footer row under the grid, on the same left edge as the first column of the lines grid above, with its `PDF, images, Word or Excel files` hint and the selected-file chips beside it, and the totals close the far end of that one row. The Add Journal Line button sits beside Use Template in the lines title row as a matching solid-border pair of the same height, radius and weight. Read-only approval comments stay in the Additional details disclosure. Do not build an attachment showcase (icon, title, size hints and a large drop area), and never add a notes field or any other key to the stored journal record to hold attachments; the journal record shape is a frozen contract. Keep this page's footer to the save action and the single primary action: it carries `Save draft` (or `Save changes`) and `Post journal`, with no Cancel button, no gate explanation paragraph, and no three-dot More actions menu, because the header back control already leaves the form and Duplicate and Reverse entry live on the register rows and the detail screen. Gate `Post journal` on the posted values alone - balanced totals inside an open accounting period - and never require an approved status here; a Draft journal is approved from the journal detail screen through its Submit for approval, Approve and Post actions.
- Put searchable entity selection in a combobox that shows identity, code and classification, and supports keyboard search, recents and favourites.
- Reuse one searchable selection control instead of rebuilding it per form: the Create Account / Edit Account drawer picks the Account Group with `src/AccountGroupPicker.jsx`, the same combobox the Journal lines account cell uses, over the DOM-free `src/account-group-search.js` and styled by its own `.agp` stylesheet so the drawer's `.am-create-drawer .am-field input` rule cannot restyle it. It groups options by account type, matches label, type, purpose and group text case-insensitively, drops any section that loses every option, and keeps `role="combobox"` / `role="listbox"` / `role="option"`, Arrow/Enter/Escape and outside-click closing identical to the journal picker. Because its host field is a `label`, this picker never nests a label inside its own popup and cancels the default action of clicks inside its root: a label fires a click on its labelled control for clicks on non-interactive descendants, which would reopen the list from an option row. Keep the visible field label outside the picker root so it still opens the picker.

## Responsive behavior

- Sidebar becomes a controlled drawer on narrow screens.
- Header actions may simplify but core navigation and creation remain available.
- Cards reflow without clipped values or text overlap.
- Wide tables retain accessible horizontal scrolling and may hide secondary columns whose values remain available in details.
- Interactive targets should be approximately 40–44px where practical.
- Period History collapses from a full desktop table to compact scrolling and then to a card list, with each card carrying period, organisation, branch, status, closing metadata, and its row actions.

## Accessibility

- Provide semantic headings, table headers, labels, button names, status text, and visible focus states.
- Icon-only controls require accessible names and tooltips where meaning is not obvious.
- Maintain adequate foreground/background contrast.
- Drawers and modals require close controls, Escape/focus management in production, and focus restoration.
- Side drawers open from the right throughout the application. They use a dimmed backdrop, a left border and negative-x shadow, isolate nested `header`/`aside` elements from shell positioning, remain viewport-bound, and become full width on small screens. Centered confirmation/action dialogs remain modals and are not converted into drawers.
- `ui-quality-polish.css`, loaded after module styles, is the authoritative placement layer for side drawers. New modules should reuse the existing drawer families instead of adding a left-edge override.
- Announce validation and asynchronous state changes to assistive technology.

Templates preserve document type/status, company logo, statutory identity, customer details, item table, taxes, totals, amount in words, notes, and signature. Template changes never recalculate or repost accounting.

Document detail pages use a separate arrow-led breadcrumb above the document identity. The identity row includes document type, number, party, and a semantic lifecycle badge. Actions are ordered by task importance: one primary next action, neutral secondary actions, and a restrained destructive action. Four compact summary metrics precede a tab strip. The Overview tab places document information and amount summary side by side on wide screens and stacks them on small screens without removing data. Items, Payments, Accounting, and Audit content remain accessible from their existing tabs.
Period Closing is a focused register rather than a dashboard of summary cards. Its feature stylesheet must explicitly reset nested `header` and `aside` positioning because legacy global selectors otherwise make those elements fixed. The Period Locking Settings panel renders inside the same drawer host as `.pls.pls-popup`, which resets its legacy full-page positioning so the drawer and not the panel owns the geometry. At desktop widths it begins after the 270px navigation rail and below the 59px application header; on narrow screens it uses the full content width and preserves horizontal access to the accounting table.
## Application-wide UI quality layer

`src/ui-quality-polish.css` is the final, UI-only compatibility layer loaded by `src/main.jsx`. It normalizes focus, hover, active and disabled states; 40px form controls; readable table density; status semantics; viewport-safe overlays; toolbar wrapping; deliberate empty states; reduced-motion behavior; and the shared 270px navigation/58px header portal geometry. It must not contain persistence, accounting, calculation, route, permission, or workflow logic.

Responsive safeguards target 1440px desktop through 1280px and 1024px laptop/tablet layouts, then collapse dashboard portals and form grids below the existing mobile navigation breakpoint. Tables retain local overflow only when their columns cannot reflow safely; the page body remains protected from horizontal overflow.
