# Transaction Register

**Last verified:** 2026-09-29

> **Report toolbar update — 2026-09-29:** the heading action row now carries a date-range preset dropdown (`All dates`, `Today`, `This week`, `This month`, `This year`, `Custom selection`) beside the search box and the `Filters` disclosure, and ONE `Export` button whose dropdown holds the report own exports. Where a sentence below still describes `Export Excel` and `Export PDF` as two side-by-side buttons, the dropdown supersedes it. See `docs/REPORT-TOOLBAR.md`.

`src/TransactionRegister.jsx` is the report page and `src/transaction-register.js` is its pure projection. The report is a document index, not a second accounting report: it answers one question - which business transactions and documents exist, and where is each one opened - so a user can find, review and open any business transaction in one place. It states every transaction ONCE with the amount its own document carries, and it never prints debit or credit. Those lines belong to the Day Book, the General Ledger and the Journal register, so the register deliberately keeps no accounting-impact drawer, no voucher detail and no second document page of its own. It is read-only: it never posts, edits, reverses, recalculates or creates anything, and it changes no accounting logic.

The register joins the four stores a business transaction can live in rather than inventing a record of its own. `src/TransactionRegister.jsx` reads `readAccounts()` (`src/account-store.js`, which merges the demo store keys into the accounting state so invoices, receipts, credit notes, purchase bills, debit notes, vendor payments and journals are all reachable), `readOperations()` (`src/operations-store.js`, the expense claims), `BANKING_KEY` (`wayvida-banking-v1`, `src/banking-service.js`, the bank statement lines) and `MANUAL_JOURNAL_KEY` (`wayvida-manual-journals-v2`, `src/simple-journal-transaction.js`, the manual journals). The projection itself is pure - the page reads the stores and passes them in - so what it collects can be tested without a browser. Nine types are collected: Sales Invoice, Credit Note, Customer Receipt, Purchase Bill, Debit Note, Supplier Payment, Expense, Journal and Bank Transaction. Sales orders and purchase orders are deliberately absent: an order is a commitment rather than a transaction and it never reaches the books. A store that is absent or unreadable is not an error, so the report still states every other transaction.

One row per transaction is a guarantee, not an assumption. A single business event often leaves two records behind: the document and the journal the engine posted for it. The documents are collected first, each one naming the journal it posted (`journalId`), and that set of journal ids suppresses the accounting rows that would otherwise duplicate them; a manual journal is the mirror image, because the manual record is the document and its ledger entry is suppressed through its own `ledgerJournalId`. Journals a document claimed therefore never appear a second time as Journal rows, and only the ones left over - opening balances, adjustments, anything posted outside a module - are listed as Journal, keyed by their own id or `token`. A final pass de-duplicates by row id and sorts newest first, so a document and its journal can never both appear.

The status vocabulary is the five lifecycle words the register filters and counts by: Draft, Pending, Posted, Reversed and Cancelled. Every document is reduced to one of them by its stored status plus its own module's "is it posted?" rule, because the same word means different things in different modules. A cancelled, cancelled, voided or excluded document is dead whatever else it says; a reversed document was posted and then corrected; a true posted flag makes it Posted; an unposted document that names a waiting state - pending, pending approval, submitted, unmatched - is Pending; anything else is Draft. A receipt is posted only when its status is Posted, a credit note, debit note or purchase bill only when its `posted` flag is set, a vendor payment the moment it is recorded, an expense only when its status is Posted, a manual journal when it is Approved, and a bank line when it is Matched or Categorized and Pending while it is Unmatched. A purchase bill's stored status is a PAYMENT status - Unpaid, Partially Paid, Paid - so the posted flag, not the word, decides its lifecycle; those payment words are document-level money states and are never invented as register statuses.

Search and filters are the shared report pattern. The heading carries a 300px search beside one Filters disclosure and the two export actions, and the disclosure owns Date from, Date to, Transaction type, Status, Branch, Customer, Supplier and the order control. Both date bounds are inclusive. The Customer and Supplier filters narrow the same party column by kind: a row states whether its party is a customer or a supplier, so a sale and a purchase are selected from one column without a second list. Type, Branch, Customer and Supplier options are derived from the collected rows, so a filter can never offer a value no transaction carries, and the Branch list is the union of the working context's accessible branches with the branches the rows actually hold. Search reads the document number, reference, party, description and type, and it is deferred so typing never blocks the table. Clear filters resets every filter, the search, the order and the page together, and the Filters button carries a count badge of the active filters.

The order control - Newest first, Oldest first, Highest amount, Lowest amount and Document number - sits inside the Filters panel rather than on the heading, so the four heading controls the report is specified with (Search, Filters, Export Excel, Export PDF) stay exactly where they are. It re-sorts the rows already in hand and never re-reads a store: `sortTransactions` copies the list, and every ordering falls back to the document number so two documents dated the same day keep one stable order instead of swapping on each render. Date descending is the default and is the order the projection itself returns, so choosing Newest first changes nothing. Changing the order counts on the Filters badge the way the purchase register counts its own Sort control, and Clear filters returns it to Newest first. Searching, filtering, re-sorting or changing the page size returns to the first page; nothing else is reset, so a search never clears a filter and paging never clears either.

The four summary cards are Total Transactions, Posted, Draft and Cancelled, and they count the FILTERED rows, so every card moves with the filters and the four always add up to the total stated first. Draft includes the documents that have not posted yet, including the ones waiting for approval, and Cancelled includes the reversed ones, because the register keeps the five lifecycle words but the four cards the report is specified with and nothing is counted twice. There is no financial KPI card: a total amount, a cash figure or an aging figure belongs to the accounting reports, not to a document index.

The table is eight business columns - Date, Transaction Type, Document No., Customer / Supplier, Reference, Amount, Status and Actions - and the widths are positional, adding up to 100% over a fixed table layout. Amount is the document total through the application's own `money()` formatter and is never mixed with a debit or a credit; the register prints no accounting impact anywhere. Status is the shared `StatusPill` with the lifecycle word printed beside its tone, so a status is readable without relying on colour. A caption states how many transactions the filters left out of how many exist, and each row's title repeats the type, number, party and reference for the columns dropped at a narrow width. Actions holds one View button per row, and the Document No. is a link-styled control (`button.trLink`) that opens the same document, so the row has a primary handle as well as a named action.

The rows are meant to be read, so the page is deliberately not compressed. Each cell keeps to one line and carries its own weight in the hierarchy: the Date is 12px and muted, the Transaction Type is normal, the Document No. is bold and link-styled, the party is bold, the Reference is muted, and the Amount is bold and right-aligned with `tabular-nums`. A long party name or reference shortens with an ellipsis instead of wrapping the row into three lines, and the full value stays on that cell's `title` and in the export; the fixed table layout is what makes the ellipsis possible, so the party, reference, type and date columns keep `overflow:hidden` with `text-overflow:ellipsis`. Row padding is 13px by 16px, the comfortable step above the Balance Sheet's 11px by 14px because this table carries eight columns rather than five. Dates read in the one format every register uses - `new Date(value+'T00:00:00').toLocaleDateString('en-IN',{day:'2-digit',month:'short',year:'numeric'})`, the same expression the Journal Entries, General Ledger, Sales Order and Budget registers state - and amounts carry two decimals from the shared formatter. The projection keeps ISO dates so the filters stay string-comparable; only the page formats them.

Paging replaces the long table. The register shows twenty-five rows at a time by default and offers 25, 50 and 100 through the shared `.pagination-footer` the journal, inventory and purchase registers already use, so the pager reads `Showing 1-25 of 113 transactions` beside the page size and `Page 1 of 3`. There is no grand total: an invoice, a receipt and an expense do not add up, and any total would change with the page. A row off the current page is hidden with `.trOffPage` rather than dropped from the document, and the print block releases it - so the PDF still states the whole filtered dataset while the screen stays one comfortable page.

View opens the source document through the routes and handshakes that already exist. `TRANSACTION_SOURCES` names, per type, the page it is opened on and the `sessionStorage` handshake that page already reads: Invoices and `wayvida-open-invoice`, Credit Notes and `wayvida-open-credit`, Payments Received and `wayvida-open-receipt`, Purchase Bills and `wayvida-open-bill`, Debit Notes and `wayvida-open-debit-note`, Expense Claims and `wayvida-open-expense`, Journal Entries and `wayvida-open-journal`, and Bank Transactions and `wayvida-open-bank`. The value handed off is `handoffId`, which is not always the record's own id: the Banking feed is selected by BANK ACCOUNT, so a statement line hands off the account it belongs to rather than the line, which the Banking page cannot resolve as a selection. A supplier payment has no document page of its own by design - a payment is recorded from its posted bill - so it opens Payments Made with no handshake, exactly as the Day Book already opens that collection. Nothing here is a second document page, and the only write the page performs is the handshake that names the record to open.

The shell is the report family's, not a new one. `src/transaction-register.css` declares `.transactionPortal`, the fixed dashboard portal every report is rendered into, and `.transactionPortal:has(.trPage)` neutralises it so the page scrolls with the shell and prints as a document instead of inside a fixed frame. The heading is a `header` element, so `.trHead` restates `position:static!important;inset:auto!important;z-index:auto!important;height:auto!important` or the fixed application header geometry lifts it out of the flow and over the summary cards. The page itself never scrolls horizontally; `.trTableScroll` is the only horizontal scroll container. The table keeps its fixed layout at EVERY width, because that is what makes the ellipsis truncation real and what stops a long party name from pushing the Status or Actions column out of reach; only the positional widths change as columns are dropped. Below 760px the Reference column is dropped and `min-width` is 640px; below 560px the Customer / Supplier column is dropped too, `min-width` is 520px, and the Actions column widens to 19% while the View control drops its label to its icon (`<span>View</span>` is hidden), so the action is never clipped at any width. The Banking screen's "View posted book register" disclosure (`.bankBookRegister`) is suppressed from this register because that panel restates transactions already recorded in the books.

The four page states reuse the existing patterns rather than inventing new ones: the loading state is the deferred-search caption and the page's `aria-busy`, the empty state is the shared `EmptyState` with different copy for "no transactions at all" and "no transactions match your filters", and the error state is an alert with a Retry action that re-reads the stores. The page refreshes on the shared `wayvida-accounts-updated` event, on `storage`, and on the explicit Refresh action. Export Excel writes the visible rows through the shared `excelReport` and `downloadReport` helpers, and Export PDF is the application's print path; both are disabled when nothing is visible, both state the organisation, branch, date range, the applied filters, the transaction count, the generator and the generation time, and both carry only the rows the filters left visible - an unfiltered control is not listed as an applied filter.
